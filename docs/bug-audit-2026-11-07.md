# ผลตรวจระบบ MUE2MUEDEE — 7 พฤศจิกายน 2026

## ขอบเขตและวิธีตรวจ

ตรวจโค้ด Backend/Frontend ตามเมนูระบบ และเรียก HTTP API ผ่าน controller จริงพร้อม JWT ใน test host ที่ใช้ฐานข้อมูล EF Core InMemory แยกเฉพาะการทดสอบ ไม่เรียก Program.cs จึงไม่รัน startup seeding หรือเชื่อมฐานข้อมูลร้านค้าจริง ไม่ deploy และไม่แก้ข้อมูลธุรกรรมเดิม

ผลนี้เป็นการตรวจโค้ดและ automated tests ไม่ใช่การรับรองว่าทุกหน้าจอและทุกกรณีปราศจากบั๊ก

## ประเด็นที่ยังเปิดอยู่

1. **นโยบาย Staff กับข้อมูลต้นทุน/กำไรยังไม่สอดคล้องกัน**: ข้อความในหน้าจัดการผู้ใช้ระบุว่า Staff ไม่เห็นต้นทุน/กำไร แต่ API ของคลัง/ขาย/ต้นทุนยังคืนข้อมูลเหล่านี้ให้ผู้ใช้ที่ authenticate แล้ว ส่วน Analytics ซ่อนข้อมูลตาม role อยู่แล้ว ต้องกำหนดขอบเขตสิทธิ์ให้ตรงกันทั้ง API และ UI; รอบนี้ยังไม่ได้เปลี่ยนสัญญา DTO/สิทธิ์ทางธุรกิจส่วนนี้
2. **การทำรายการพร้อมกันกับ PostgreSQL ยังไม่ได้ยืนยัน**: การออกเลขมี unique constraint แต่การอ่านเลขล่าสุดแล้วเพิ่มยังอาจชนเมื่อหลาย request มาพร้อมกัน; RowVersion ปัจจุบันเป็น bytea ที่ตั้ง IsRowVersion และยังไม่ได้ยืนยันกลไกสร้างค่าในฐานข้อมูลจริง ต้องมีการทดสอบ PostgreSQL แยกสำหรับการขายสินค้าชิ้นเดียวกันพร้อมกัน การออกเลข และการรับเข้าคลังซ้ำ

## ข้อจำกัดของผลตรวจ

- InMemory ไม่บังคับ unique/FK/transaction และพฤติกรรม query บางอย่างเหมือน PostgreSQL ทุกกรณี จึงใช้ผลนี้แทน integration test กับ PostgreSQL ไม่ได้
- ยังไม่ได้คลิกตรวจทุกหน้าจอผ่าน browser, ทดลองสแกนกล้อง/เครื่องอ่านจริง หรือพิมพ์กับเครื่องพิมพ์จริง
- LocalImageStorage ทดสอบอ่าน/เขียนไฟล์แล้ว; ไม่ส่งรูปไป Cloudinary จริงและไม่ทดสอบการ redeploy hosting
- ไม่แก้ข้อมูลเก่าที่เคยมีต้นทุนคลาดเคลื่อนหรือสถานะผิดอัตโนมัติ และไม่เปลี่ยนไฟล์ SQL seed ที่มีอยู่ก่อนงานนี้
