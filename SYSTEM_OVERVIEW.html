ภาพรวมระบบและเทคโนโลยีที่ใช้ (System Overview & Tech Stack)

1.1 หน้าที่หลักและความสามารถของระบบ

MUE2MUEDEE (มือสองมือดี) เป็นระบบ ERP และ POS แบบหลายร้านค้า (Multi-Tenant SaaS) ที่ออกแบบเฉพาะสำหรับร้านซื้อ-ขายกล้องถ่ายภาพ เลนส์ และอุปกรณ์ถ่ายภาพมือสอง ซึ่งแตกต่างจากระบบขายสินค้าทั่วไปตรงที่สินค้าทุกชิ้นมีเอกลักษณ์เฉพาะตัว ต้องติดตามด้วย Serial Number และ SKU รายชิ้น พร้อมคำนวณต้นทุนแฝงจริงหลังรับซื้อ (ค่าซ่อม ค่าล้างเซนเซอร์ ค่าขนส่ง)

📥 รับซื้อ & ตรวจสภาพ (PO Wizard)

  • ประเมินสภาพตาม Checklist มาตรฐานแยกตามหมวดกล้องและเลนส์
  • คำนวณ Max Buy Price อัตโนมัติ (Target Margin 15%)
  • ระบบส่งอนุมัติ Owner/Admin เมื่อเสนอราคาเกินเพดาน
  • พิมพ์สัญญาซื้อขายและสร้าง SKU นำเข้าคลังอัตโนมัติ

📦 คลังสินค้า & ต้นทุนรายชิ้น

  • จัดการคลังสินค้ารายชิ้นผูก Serial Number และ RowVersion
  • บันทึกต้นทุนแฝงย่อย (ซ่อม/ล้าง/ส่ง) เพื่อคำนวณ Actual Cost
  • Pricing Engine แนะนำราคาขายและส่วนลดตามอายุสต็อก
  • ออกแบบและพิมพ์ป้ายสติ๊กเกอร์บาร์โค้ด/QR (1–3 คอลัมน์ & A4)

🛒 ขายหน้าร้าน (POS) & หน้าร้านออนไลน์

  • สแกนบาร์โค้ดด้วยเครื่องยิงหรือกล้องเว็บแคม (@zxing/browser)
  • รับชำระเงินหลายช่องทางในบิลเดียว (Multi-Tender Payments)
  • สืบค้นประวัติเครื่องตลอดอายุขัย (Serial Trace)
  • เผยแพร่แคตตาล็อกหน้าร้านสาธารณะ (/shop/:storeCode)

2.2 กลไก Multi-Tenancy Isolation และความปลอดภัยในระดับ DbContext

ระบบรองรับการทำงานหลายร้านค้าภายในฐานข้อมูลเดียว (Shared Database, Discriminator Column store_id) โดยใช้กฎเหล็กตามมาตรฐานความปลอดภัยว่า ห้ามเชื่อถือ StoreId ที่ส่งมาจาก Client Body แต่ให้ยึด store_id จาก JWT Claims ของผู้ใช้ปัจจุบันเป็นหลัก

แผนภาพที่ 2.2: กลไกการแยกข้อมูลหลายร้านค้า (Tenant Isolation) และ Audit Trail อัตโนมัติ (ลากเพื่อเลื่อน • กดปุ่มเพื่อซูม) 
flowchart LR
    Req["HTTP Request + Bearer JWT"] --> Decode["JwtBearer Middleware<br/>Validate Signature & Expiry"]
    Decode --> Claims["CurrentUser / CurrentStore<br/>อ่าน store_id, role, user_id, is_super_admin"]
    Claims --> ReadOrWrite{"ประเภทคำสั่ง"}
    ReadOrWrite -->|"Query (อ่านข้อมูล)"| QueryFilter["EF Core Global Query Filter<br/>!IsDeleted && (StoreId == _currentStore.StoreId)"]
    ReadOrWrite -->|"SaveChangesAsync (บันทึก)"| GuardTenant["1. Auto-assign StoreId เมื่อ Added<br/>2. ห้ามแก้ไข StoreId เดิม (Throw Error)"]
    GuardTenant --> AuditFields["3. กำหนด CreatedAt / UpdatedAt<br/>4. แปลง Delete เป็น Soft Delete (IsDeleted=true)"]
    AuditFields --> AuditLog["5. สร้าง AuditLog อัตโนมัติ<br/>บันทึก OldValues / NewValues แบบ JSON"]

    AuditLog --> DB
คำอธิบาย: ทุก Entity ที่สืบทอด ITenantEntity จะถูกกรองด้วย Global Query Filter อัตโนมัติใน ApplicationDbContext.OnModelCreating() และทุกการเปลี่ยนแปลงข้อมูล (ยกเว้นตาราง AuditLog และ RefreshToken) จะถูกบันทึกประวัติ Old/New JSON ลงตาราง audit_logs เสมอ

ขั้นตอนการทำงานหลักของระบบ (Core Workflows)

3.1 การยืนยันตัวตน การหมุนเวียน Refresh Token และการสลับร้านค้า

ระบบจัดการ Identity รองรับผู้ใช้ 1 คนสังกัดหลายร้านค้าในบทบาทต่างกัน (ผ่านตาราง user_stores) รวมถึงบัญชี Super Admin ที่เข้าดูร้านค้าที่เปิดใช้งานอยู่ทั้งหมดได้โดยไม่ต้องสร้างสมาชิก UserStore

แผนภาพที่ 3.1: ลำดับการเข้าสู่ระบบ, การต่ออายุ Token และสลับร้านค้า (Sequence Diagram) (ลากเพื่อเลื่อน • กดปุ่มเพื่อซูม) 
sequenceDiagram
    autonumber
    actor User as ผู้ใช้งาน (Browser SPA)
    participant AuthCtrl as AuthController
    participant AuthSvc as AuthService
    participant Security as PasswordHasher / JwtTokenService
    participant DB as PostgreSQL

    Note over User,DB: 1. ขั้นตอนการเข้าสู่ระบบ (Login)
    User->>AuthCtrl: POST /api/auth/login (usernameOrEmail, password)
    AuthCtrl->>AuthSvc: LoginAsync()
    AuthSvc->>DB: Query User + UserStores + Store
    DB-->>AuthSvc: User Entity (IsActive=true)
    AuthSvc->>Security: VerifyPassword(password, PasswordHash)
    Security-->>AuthSvc: Valid
    alt เป็นบัญชี Super Admin
        AuthSvc->>DB: ดึงทุกร้านค้าที่ IsActive = true
    else เป็นผู้ใช้ระดับร้านค้า
        AuthSvc->>AuthSvc: เลือกร้านแรก (ให้ความสำคัญ Role = Owner ก่อน)
    end
    AuthSvc->>Security: GenerateAccessToken(user, storeId, role) + GenerateRefreshToken()
    AuthSvc->>DB: บันทึก RefreshToken (อายุ 7 วัน)
    AuthSvc-->>User: LoginResponse (accessToken, refreshToken, activeUserStores)

    Note over User,DB: 2. ขั้นตอนการสลับร้านค้า / สาขา (Switch Store)
    User->>AuthCtrl: POST /api/auth/switch-store (storeId) + Bearer JWT
    AuthCtrl->>AuthSvc: SwitchStoreAsync()
    AuthSvc->>DB: ตรวจสอบสิทธิ์เข้าถึงร้านปลายทาง
    AuthSvc->>Security: ออก JWT Access Token ใหม่ที่ผูก store_id & role ใหม่
    AuthSvc->>DB: บันทึก RefreshToken ใหม่
    AuthSvc-->>User: LoginResponse ใหม่ (Frontend รีโหลดไปยัง /dashboard)

    Note over User,DB: 3. ขั้นตอนการต่ออายุ Token (Refresh Token Rotation)
    User->>AuthCtrl: POST /api/auth/refresh (refreshToken)
    AuthCtrl->>AuthSvc: RefreshTokenAsync()
    AuthSvc->>DB: ตรวจสอบ RefreshToken (ยังไม่ Revoked และไม่ Expired)
    AuthSvc->>DB: Revoke RefreshToken เดิม (RevokedAt = UtcNow)
    AuthSvc->>Security: ออก Access Token + Refresh Token ชุดใหม่
    AuthSvc-->>User: LoginResponse ชุดใหม่
คำอธิบาย: เมื่อสลับร้านค้า ระบบจะออก Access Token ใบใหม่ที่มี Claim store_id และ role ประจำร้านนั้นทันที เพื่อให้ Global Query Filter แยกข้อมูลคนละร้านอย่างเด็ดขาด

3.2 กระบวนการรับซื้อ ตรวจสภาพ ประเมินราคา อนุมัติ และนำเข้าคลัง (Purchase 4-Step Flow)

การรับซื้อกล้อง/เลนส์จากลูกค้าผ่านหน้า /purchase/new ถูกควบคุมด้วย State Machine ใน PurchaseService.cs เพื่อป้องกันการรับซื้อเกินราคาตลาดโดยไม่ได้รับอนุญาต และสร้างรหัส SKU เข้าคลังอัตโนมัติ

// สูตรคำนวณเพดานราคารับซื้อสูงสุดที่แนะนำ (PurchaseService.CalculateMaxBuyPrice)
BaseMax = ExpectedSalePrice × (1 - 0.15) - EstimatedRepairCost - EstimatedCleaningCost - MissingAccessoriesDeduction
MaxBuyPrice = Math.Floor(Math.Max(0, BaseMax) / 100) × 100 // ปัดลงหลักร้อย (100 บาท) และตั้ง NeedsApproval = true หาก OfferedPrice > MaxBuyPrice
แผนภาพที่ 3.2: กระบวนการรับซื้อ ตรวจสภาพ อนุมัติราคาพิเศษ และนำเข้าคลังสินค้า (ลากเพื่อเลื่อน • กดปุ่มเพื่อซูม)

3.3 การบันทึกต้นทุนแฝงและการคำนวณราคาขายตามอายุสต็อก (Costing & Pricing Engine)

หลังนำสินค้าเข้าคลัง หากมีค่าใช้จ่ายเพิ่มเติม (เช่น เปลี่ยนยางบวม ส่งซ่อมม่านชัตเตอร์ ล้างราเลนส์) ระบบใน PricingService.cs จะบวกต้นทุนเหล่านั้นเข้ากับ ActualCost อัตโนมัติ และคำนวณราคาแนะนำใหม่พร้อมปรับส่วนลดตามอายุสต็อก (Aging Buckets)

// สูตร Pricing Engine (PricingService.CalculateFormula)
BaseRecommended = ActualCost / (1 - TargetMarginDecimal) // เช่น 25,000 / (1 - 0.15) = 29,412 บาท
RecommendedPrice = Math.Max(ActualCost, Math.Round(BaseRecommended × (1 - AgingDiscount%), 0))
MinimumPrice = Round(ActualCost / 0.95, 0) | MaximumPrice = Round(ActualCost / (1 - Min(0.80, TargetMargin + 0.10)), 0)

5.2 สรุปหน้าที่ของโฟลเดอร์และไฟล์สำคัญ

โฟลเดอร์ / ไฟล์ ความรับผิดชอบหลัก
Mue2MueDee.Domain/Common/BaseEntity.cs กำหนด Contracts พื้นฐาน ได้แก่ BaseEntity<TId>, AuditableEntity<TId>, ITenantEntity (บังคับคอลัมน์ StoreId) และ ISoftDelete
Mue2MueDee.Application/Services/ ศูนย์รวม Business Rules ทั้งหมด เช่น การคำนวณ MaxBuyPrice ใน PurchaseService, สูตร PricingService, การตัดสต็อกและคืนสต็อกใน SaleService
Mue2MueDee.Infrastructure/Persistence/ รวม ApplicationDbContext.cs ที่บังคับ Global Query Filter, Audit Trail, Soft Delete และการตั้งค่าคอลัมน์แยกตาม Entity ใน Configurations/
Mue2MueDee.Web/Controllers/ รับ HTTP Request, แปลงผลลัพธ์ผ่าน ApiControllerBase.Success() / CreatedSuccess() รวมถึง UploadsController ที่จำกัดนามสกุลและขนาดไฟล์ (10 MB/ไฟล์)
spa/src/app/core/ ศูนย์กลางระบบความมั่นคงฝั่งหน้าเว็บ: แนบ JWT Bearer Token ผ่าน auth.interceptor.ts, รีเฟรช Token อัตโนมัติ, จัดการ Global Loading และ Toast Notifications
spa/src/app/shared/components/ ชุด Standalone Form & UI Components ที่ Implement ControlValueAccessor ครบทุกตัว พร้อมคอมโพเนนต์บาร์โค้ด (app-barcode), QR (app-qrcode) และตัวอัปโหลดรูปภาพ
spa/src/app/features/ หน้าจอการทำงานทั้ง 10 ฟีเจอร์ แยกไฟล์ 3 ส่วน (.ts/.html/.css) ใช้ Angular Signals และ Feature-level Service & Models ตามกฎใน AGENTS.md
